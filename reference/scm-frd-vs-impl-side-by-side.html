At a Glance — The Core Document Flow

The single most consequential question for the SCM module: does a Purchase Requisition have to go through a Purchase Order? The FRD says yes. The code says no. Read the two diagrams and the policy gap is the difference between the green "intended" path and the purple "actual" path.

Intended FRD flow (PR §4.2.1, §4.2.4)

flowchart LR PR[PR Pending] -->|Proses| PO[PO Draft] PO -->|Kirim| POS[PO Sent] POS -->|Buat SJ| SJP[SJ Picking] SJP -->|Kirim| SJI[SJ In Transit] SJI -->|Terima Cabang| SJR[SJ Received] SJR -->|Review Admin Pusat| SJRev[SJ Reviewed] SJRev -->|Generate Invoice| INV[Invoice Unpaid] INV -->|Bayar| Paid[Invoice Paid]

Every PR becomes a PO. Every PO produces an SJ. Every received SJ produces one Invoice based on received quantity. Source: docs/Functional Requirement Document.md §4.2.1, §4.2.4.

Actual implementation

flowchart LR PR[PR Pending] -->|alsoCreateSJ true| SJP[SJ Picking] PR -->|alsoCreateSJ false| SJP PR -.->|PO path terpisah| PO[PO Draft] PO -->|Send| POS[PO Sent] POS -->|Receive| POC[PO Completed] SJP -->|Ship| SJI[SJ In Transit] SJI -->|Terima Cabang| SJR[SJ Received] SJR -->|Review| SJRev[SJ Reviewed] SJRev -->|Generate| INV[Invoice Unpaid] INV -->|Pay| Paid[Invoice Paid]

The dotted line is the only path that actually goes through PO for internal restocking. The solid line is the default. Source: src/lib/server/scm.ts:306–390 (processPurchaseRequisition), :407–700 (PO module).

Gap: the FRD names PO as a canonical stage. The code lets you skip it. This is a defensible design (ERPNext and Odoo both treat PO as optional for internal stock transfers) but the policy is not written down anywhere — see §3.1 row on PR → PO auto-link.

1. Executive Summary

The current implementation captures the shape of the supply chain described in the FRD — PR, PO, Surat Jalan, Invoice, stock transfer, supplier delivery, yield tracking, waste, and SO are all present as distinct modules with their own tables and UI. The most consequential gaps are in the SCM state machine discipline and in the FRD's prescribed audit controls, not in feature presence.

Working as the FRD intends
  • Document hierarchy (PR → SJ → Invoice) with inventory gated on physical movement
  • In-transit virtual warehouse as a separate table (in_transit_inventory)
  • Invoice quantity = receivedQuantity, not quantity or pickedQuantity ("actual base")
  • MOQ enforcement on PR create
  • Configurable reorder formula (ROP/ROQ days) with admin-only edit
  • Blind SO: system stock stripped from response for branch_admin and admin_pusat
  • Countable flag honored when triggering SO
  • BOM cost roll-up on ingredient price change, supplier delivery, and SJ receive
  • Yield Costing formula uses post-shrinkage target weight, not source weight
  • Negative-stock soft block on POS + alert to Area Manager
  • 3-pillar SJ detail view (Order | Ready | Picked) plus Received and Rejected
  • Period close blocks on negative inventory, pending cancel requests, unpaid invoices, pending SO
Gaps that will bite at scale
  • PO is optional in the internal restocking path. FRD §4.2 names PO as a required stage. The current processPurchaseRequisition can create an SJ directly without a PO.
  • Quarantine is named, not modeled. The DN item can record Quarantine disposition, but no quarantine_inventory table exists. A "quarantined" item is just a ledger note.
  • Fulfilled status is unreachable. Fulfilled exists in the PR status enum but no code path ever sets it.
  • PR auto-create of SJ silently uses pr.branchId as fallback fromBranchId if the central warehouse lookup fails — a branch would ship stock to itself.
  • Branch admin receive on an SJ can mutate the "current system stock" via approved SO without the corresponding ledger balance being re-derived — the ledger balance reflects the post-SO quantity, but other paths deduct from a possibly stale inventory.quantity until the SO approval transaction is fully atomic (it is, in current code — but worth flagging for race conditions under concurrent writes).
  • Pre-Open Report from FRD §4.1 is not produced before opening a new period.
  • Audit trail is inconsistent. logAudit is called on most status transitions but not uniformly on edits to PR/SJ items, on supplier-delivery update, or on stock-transfer ship/receive (only on status changes).
  • Period lock is not enforced as a write guard in POS, SCM, inventory, waste, or SO. The close checks surface negative inventory and pending state, but the server functions do not refuse writes after closePeriod.
  • Stock transfer approval moves inventory instantly in the current shipStockTransfer and the original approveStockTransfer. The schema supports In Transit, and the UI now has a Ship step, but the approval is combined with the deduction in a single transaction — there is no two-step approval → ship separation that the FRD's "approval first" language implies for mutasi.
  • Print Bill (FRD §3.2) is implemented in pos-print.ts, but the surface area to call it from POS is wired through the receipt generator only; a "Print Bill" button is not a first-class CTA on the cart.

2.2 Opname Stok (Stock Opname)

SO state machine (intended vs actual)

Intended (FRD §4.3)

stateDiagram-v2 [*] --> Submitted: trigger then count Submitted --> Investigasi: variance exists Investigasi --> Approved: AM accepts recount Investigasi --> Submitted: recount required Approved --> [*]

FRD intends an auto-promotion to Investigasi whenever variance exists. The diagram shows two valid terminals; only Approved is final.

Actual

stateDiagram-v2 [*] --> Submitted: submitStockOpname Submitted --> UnderInvestigation: markStockOpnameInvestigation - manual UnderInvestigation --> Submitted: updateStockOpnameCounts Submitted --> Approved: approveStockOpname UnderInvestigation --> Approved: approveStockOpname Approved --> [*]

Promotion to UnderInvestigation is manual (super_admin or area_manager). The auto-promote on variance > 3% rule is not implemented. The actual enum name is Under Investigation, not Investigasi.

FRD says Implementation Best practice & source
§4.3 — SO trigger only by AM / Admin Pusat; system records who triggered and when.
OK 		triggerStockOpname restricts roles to super_admin, admin_pusat, area_manager. stockOpnames.triggeredBy + triggeredAt are set. Source: src/lib/server/inventory.ts:131–170. This is the standard SO control pattern. Toast and Square for Restaurants both gate SO on supervisor roles.
§4.3 / §4.4 — Branch admin uses blind SO: cannot see expected value; submit blocked when blank.
PARTIAL 		Blind stripping is in getStockOpnameDetail by setting isBlind and zeroing systemStock and variance for branch_admin and admin_pusat. Blank-submit block is not server-enforced in submitStockOpname; the current handler only updates items that are passed in. Items not in the SO rows remain with physicalStock: 0. Source: src/lib/server/inventory.ts:200–280. Two industry patterns exist: (1) reject submission when any countable item is missing a physical count, (2) accept partial submissions and treat missing as 0. The FRD wants pattern 1. ERPNext enforces blank-submit lock at the form layer; Odoo enforces at the ORM layer by requiring a value before the state transition.
§4.3 — Status "Investigasi" if variance exists.
PARTIAL 		markStockOpnameInvestigation exists and is restricted to super_admin/area_manager. But submitStockOpname always sets status to Submitted; an SO is never automatically marked Investigasi on submission. Variance is recorded per item but does not promote the SO row to Investigasi. Source: src/lib/server/inventory.ts:282–360 (submit + markInvestigation). Auto-promotion to Investigasi on variance above a threshold (e.g., >3% per FRD §6.2.2) is the ERPNext pattern. The "Discrepancy >3% highlight" mentioned in the FRD module description (§3.1) is partially implemented: variancePercentage is stored per item, but no UI rule highlights items >3%.
§4.4 — Variance calculation only in background; visible to AM in Audit module.
OK 		Variance is computed at submit time using the frozen systemStock snapshot. The view strips variance from blind roles. Source: src/lib/server/inventory.ts:210–240. Snapshot at trigger time, computation at submit, disclosure at review — this is the right shape.
Notes 27 Apr — Countable vs uncountable items: uncountable items (sedotan per pcs, opened galon) are not in the SO checklist.
OK 		ingredients.countable boolean is honored in triggerStockOpname: only countable = true items are inserted into stockOpnameItems. Source: src/lib/server/inventory.ts:142–160, schema line 223. This is the correct model. Uncountables belong in waste / broken-stock (FRD §5.2) not SO.

2.3 Pemborosan (Waste) & Barang Rusak (Broken Stock)

FRD says Implementation Best practice & source
§5 — Three categories only: Beban Makan, Biaya Operasional, Spoiled. Expired is removed.
OK 		waste_category enum is exactly these three. createWasteEntry validates with Zod. Source: src/db/schema.ts:66–70 and src/lib/server/waste.ts:75–90. Hard-coded enum is appropriate for the FRD's "tiga kategori tetap" rule.
§5.1.2 / §5.2 — "Biaya Operasional" auto-link to Broken Stock list.
OK 		On create, if category = Biaya Operasional, an operationalExpenses row is inserted with wasteEntryId FK. getBrokenStock joins wasteEntries ⨝ operationalExpenses for the side-by-side view. Source: src/lib/server/waste.ts:100–120, broken-stock.tsx page. The side-by-side UI in waste/broken-stock.tsx is the FRD §3.5.1 "side-by-side Broken Stock UI" with a Daftar Broken Stock table on the left and a Ringkasan Barang Keluar (with Stok Habis / Stok Berkurang badges and a link to the operational expense amount) on the right. Matches intent.
§4.4 — Automated waste valuation = quantity × master HPP.
OK 		createWasteEntry computes valuation = quantity * averageCost at write time. Source: src/lib/server/waste.ts:99–108. Snapshot-at-write is the right call. The FRD's §6.6 "Historical COGS Snapshot" pattern is the same shape — never recompute historical valuations from today's prices.
§4.4 — Investigation comment required when waste > 5%.
PARTIAL 		addInvestigationNote exists and is restricted to super_admin/area_manager. closePeriod checks waste entries with a 5% rule. But the rule uses quantity / (quantity + inventoryQty) not quantity / branchRevenue as a proxy. The 5% trigger is also not enforced at write time. Source: src/lib/server/finance.ts:455–478. ERPNext triggers a mandatory investigation note on variance > 5%. The current implementation does this at close-period, not at write, so a Period can be opened and waste recorded freely; only the next close flags it. A write-time soft reminder is the right addition.
§6.3.4 — "Spoiled" & "Biaya Operasional" → Operational Loss; "Beban Makan" → Staff Benefit Expense.
PARTIAL 		"Biaya Operasional" auto-creates an operationalExpenses row. "Spoiled" and "Beban Makan" do not create corresponding expense rows; the wasteEntries.valuation is the only persisted value. Source: src/lib/server/waste.ts:99–125. Mapping each category to a P&L line at write time is the ERPNext / Odoo pattern. A nightly job that posts valuations to a finance sub-ledger is the typical addition.

3.1 Permintaan Pembelian (Purchase Requisition)

PR state machine

stateDiagram-v2 [*] --> Draft: branch creates Draft --> Pending: submit Pending --> Approved: AM or Admin Pusat approves Pending --> Processed: Admin Pusat or super processes with SJ Pending --> Rejected: AM or Admin Pusat rejects Approved --> Processed: Admin Pusat or super processes Processed --> Fulfilled: gap - no code path Rejected --> [*] Processed --> [*] Fulfilled --> [*]

The Fulfilled state exists in the enum (src/db/schema.ts) but no server function ever sets it. In the live system a PR is therefore always one of Pending, Processed, or Rejected — the "fulfilled" terminal is unreachable. The Approved state is a brief intermediate used by AM before Admin Pusat presses "Proses".

FRD says Implementation Best practice & source
§4.1.1 — PR wajib munculkan kolom "Sisa Stok Aktual" di samping qty order.
OK 		In the PR create modal, every ingredient option shows Stok: {stockQty} (with a "⚠️ LOW" badge if below ROP) and MOQ. The list of added items also shows stock, MOQ, and a "di bawah ROP" indicator. Source: purchase-requisitions/index.tsx:303–375. Showing stock next to qty is the ERPNext / Odoo pattern. The "Sisa Stok Aktual" wording is the FRD's preferred label — consider renaming the displayed label to match.
§4.1.1 — Edit limit: branch can edit until PR is processed.
OK 		updatePurchaseRequisition for branch_admin: only Draft/Pending; after Processed, server throws. Source: src/lib/server/scm.ts:213–305. State-machine gate is the right place to enforce this. Toast and Square use the same pattern.
§4.1.1 — Approve button is renamed to "Proses" (Pusat).
OK 		Button is "Proses" and processPurchaseRequisition handles it. Source: purchase-requisitions/index.tsx:402–420. Terminology aligns with FRD's intent to separate "proceed" from "approve".
§4.2.1 — "Proses" should auto-create PO first, then SJ, then Invoice (PR → PO → SJ → Invoice).
DIFFERS 		PR processing has a flag alsoCreateSJ; if true, it creates an SJ directly in Picking status, with no PO. There is no PR → PO auto-link in this code path. The PO module exists independently and is mostly used for external supplier flows.
Source: src/lib/server/scm.ts:306–390. 		ERPNext and SAP MM treat the PR → PO → GR (goods receipt) chain as a hard sequence for external procurement, but for internal stock transfers they treat PO as optional. The right design call is to keep PR → SJ direct available but make PO a promotable step, not a hard gate, and document that policy in the FRD.
§5.3 — MOQ enforced in auto-PR generation, rounding up to MOQ.
OK 		createPurchaseRequisition validates item.quantity % ing.moq === 0 for any moq > 1. generateReorderRecommendations rounds up ROQ to MOQ: Math.ceil(recommendedQty / ing.moq) * ing.moq. Source: src/lib/server/scm.ts:163–175 and src/lib/server/reorder.ts:96. Ceiling rounding to MOQ is the correct mathematical pattern. ERPNext uses the same approach.
§5.3 — Reorder formula configurable, Super Admin–only.
OK 		app_settings rows for reorder_rop_days and reorder_roq_days. updateReorderSettings restricted to super_admin/admin_pusat. Defaults: 3 / 5. Source: src/lib/server/reorder.ts. Storing formula constants in app_settings is more flexible than baking them into the code. The FRD's stronger form (Super Admin–only, not Admin Pusat) should be tightened — current code allows admin_pusat to edit the formula.
Status Fulfilled (PR end-state).
MISSING 		Fulfilled is in the enum but no server function transitions to it. Source: src/lib/server/scm.ts:55–100 shows the enum; nothing writes it. ERPNext and Odoo both have a terminal "Done" / "Closed" PR state. Without it, PRs that have completed their lifecycle still look "in flight" in the list.

3.2 Surat Jalan (Delivery Note)

SJ state machine (the only document that moves stock)

Intended (FRD §4.2)

flowchart LR SJP[SJ Picking] -->|Kirim| SJI[SJ In Transit] SJI -->|Terima Cabang| SJR[SJ Received] SJR -->|Review Admin Pusat| SJRev[SJ Reviewed] SJRev -->|Generate Invoice| INV[Invoice]

The FRD implies a clean four-state forward path. Reject handling is described as a column on the receive form, not as a separate state.

Actual

flowchart LR SJP[SJ Picking] -->|shipDeliveryNote| SJI[SJ In Transit] SJP -->|cancelDeliveryNote| SJC[SJ Cancelled] SJI -->|receiveDeliveryNote partial| SJP2[SJ Partial Received] SJI -->|receiveDeliveryNote full| SJR[SJ Received] SJI -->|cancelDeliveryNote| SJC SJP2 -->|receiveDeliveryNote| SJR SJP2 -->|cancelDeliveryNote| SJC SJR -->|reviewDeliveryNote| SJRev[SJ Reviewed] SJRev -->|generateSCMInvoice| INV[Invoice]

Four additional paths exist in code that the FRD does not explicitly call out: cancel from Picking or In Transit, partial receive (multi-call on the same SJ), and cancel from Partial Received. These are necessary and correct, but they widen the state machine beyond the FRD's wording.

FRD says Implementation Best practice & source
§4.2.2 — 3-pillar input: Jumlah Diorder | Jumlah Ready | Jumlah Dikirim.
OK 		deliveryNoteItems carries quantity (ordered), readyQuantity, pickedQuantity, receivedQuantity, rejectedQuantity. The detail page renders Order / Ready / Picked columns explicitly. Source: src/db/schema.ts:859–875 and delivery-notes/$dnId.tsx:260–280. Five columns (3 + 2 receiver) is correct. The 3-pillar view is what ERPNext calls the "Pick List" — order, available, will-ship — and they are right to separate it from the receive-side quantities.
§4.2.2 — Edit SJ limit: Admin Pusat can edit while not dispatched.
OK 		updateDeliveryNote runs in the Picking state. shipDeliveryNote blocks edits beyond Picking. Source: src/lib/server/scm.ts:822–875. Pre-dispatch edit window is the standard pattern.
§4.2.2 — In-Transit Virtual Warehouse.
OK		 shipDeliveryNote creates in_transit_inventory rows tied to deliveryNoteId. receiveDeliveryNote deletes the in-transit row per received item. Source: src/lib/server/scm.ts:876–970 and 973–1240. In-transit as a separate bucket is the canonical pattern (SAP "In-Transit Stock", Odoo "Inter-warehouse transit"). The previous double-deduction bug (per supply-chain-fix.md §1.1) is fixed: PR processing no longer creates in-transit records.
§4.2.3 — Reject & Retur.
PARTIAL		 Three dispositions: Return to Source (returns stock to source with IN ledger + OUT ledger at destination), Scrap (auto-creates a waste entry under Biaya Operasional), Quarantine (no inventory bucket; only a ledger note). Source: src/lib/server/scm.ts:1050–1115. Return-to-Source and Scrap are correctly handled. Quarantine is a documented gap: the FRD's quarantine concept is meant to be a holding state for items that need supervisor decision. The right next step is a quarantine_inventory table (see supply-chain-fix.md §1.3) and a "release" action that promotes quarantined stock to either the destination branch or to scrap.
§4.2.4 — Invoice quantity = actual received (not ordered, not shipped).
OK 		generateSCMInvoice iterates DN items and uses receivedQuantity as the line quantity. If receivedQuantity is null, the invoice throws "Cannot create invoice with zero amount". Source: src/lib/server/scm.ts:1437–1545. This is exactly the FRD's "Actual Base" rule.
§4.2.4 — Edit Invoice allowed for Super Admin & Admin Pusat.
MISSING 		No updateSCMInvoice server function exists. Once generated, an invoice is effectively immutable. Source: src/lib/server/scm.ts:1390–1615 lists only getSCMInvoices, getSCMInvoice, generateSCMInvoice, paySCMInvoice, cancelSCMInvoice. Immutability of a generated financial document is the safer default (audit, posting, controls), but the FRD explicitly allows Super Admin / Admin Pusat to edit for discrepancy cases. The right compromise is a "reissue" pattern: cancel + re-generate, with a chained reference for audit. The current cancelSCMInvoice works only on Unpaid invoices, which is the right gate.
Notes 27 Apr — Both admin_pusat and branch_admin must "review" the latest SJ before invoice can be written.
OK 		reviewedByAdminPusat on deliveryNotes is set by reviewDeliveryNote. The detail page gates canGenerateInvoice on reviewedByAdminPusat === true. Source: src/lib/server/scm.ts:1336–1388 and delivery-notes/$dnId.tsx:122. The "review" gate is a clean four-eyes pattern. One missing symmetry: branch admin does not have an explicit "review" action — only receiveDeliveryNote. Consider an explicit branch_admin_confirmed flag for symmetry.
DN cancelDeliveryNote (cancel from Picking or In Transit).
OK 		Function exists, restricted to super_admin/admin_pusat. From In Transit, it reverses the source deduction and deletes the in-transit row. Source: src/lib/server/scm.ts:1245–1335. Reverse-on-cancel is the correct reversal pattern (mirror the OUT entry as IN, mirror the in-transit creation as deletion).

3.5 Mutasi Stok (Stock Transfer)

Stock transfer state machine

stateDiagram-v2 [*] --> PendingApproval: branch requests PendingApproval --> Approved: AM or super approves PendingApproval --> Rejected: AM or super rejects Approved --> InTransit: shipStockTransfer InTransit --> Completed: receiveStockTransfer InTransit --> Cancelled: cancelStockTransfer Approved --> Cancelled: cancelStockTransfer Rejected --> [*] Completed --> [*] Cancelled --> [*]

Stock is only moved at the Approved → InTransit transition (shipStockTransfer in src/lib/server/scm.ts:1832). Approval alone does not move stock, which is the FRD's "approval first" requirement. The InTransit → Completed transition (receiveStockTransfer in :1925) is what credits the destination branch.

FRD says Implementation Best practice & source
§4.3 / Notes 27 Apr — Branch can request transfer; AM/Super Admin must approve before the transfer can proceed.
OK 		createStockTransfer → status Pending Approval. approveStockTransfer → Approved. rejectStockTransfer → Rejected with reason. Source: src/lib/server/scm.ts:1667–1830. Approval gate before movement is the right control. The detail page (109 lines) is a single-ingredient transfer; the FRD's "from and to" suggests multi-item is allowed elsewhere — confirm whether the current single-row model is intentional.
§3.1.4 — AM scoped to assigned branches.
OK		 getStockTransfers filters to assignedBranches for AM. approveStockTransfer and rejectStockTransfer call assertBranchAccess(user, transfer.fromBranchId). Source: src/lib/server/scm.ts:1617–1665 and 1748–1756. Branch-scoped reads and writes are correctly enforced. Same pattern should be applied to processPurchaseRequisition for AM (it is, per assertBranchAccess(user, pr.branchId) at line ~337).

7. Recommended next steps (priority order)

  1. Period lock as a write guard. One helper, applied to every write function. Prevents a class of period-end bugs that are hard to recover from. (FRD §4.1.)
  2. Quarantine inventory bucket. A holding "branch" for quarantined items, with a release action. Unblocks the DN reject flow from the FRD. (FRD §4.2.3.)
  3. Pre-Open Report + Closing Preview Report. Two reports in finance.ts that close the FRD's period-control narrative.
  4. PR Fulfilled transition + Edit Invoice (reissue pattern). Two small additions that close the SCM state machine.
  5. SO auto-promote to Investigasi on variance > 3% + blank-submit guard. Two small changes in submitStockOpname.
  6. UoM conversion table for multi-level (Sak → Kg → Gram). Required by FRD §3.1.4 worked example.
  7. Spoiled & Beban Makan → P&L. Mirror the Biaya Operasional auto-link for the other two categories, with the FRD's P&L mapping.
  8. Reorder formula edit restricted to Super Admin (drop Admin Pusat from the allow list).
  9. AM Supply Chain nav collapsed to a read-only view (single page with PR + SJ + Invoice + Mutasi in tabs, no actions).

8. Verifying the best-practice claims

The right-hand column above draws on the following widely-cited references. None of these are a "live web search" result for this session — they are stable, well-known industry patterns. If you want to extend any claim, these are the natural starting points.

  • ERPNext Stock — frappe.io/erpnext/docs/en/stock — append-only stock ledger, multi-UoM, item variants, BOM explosion, Stock Entry as a paired IN/OUT document.
  • Odoo Inventory & MRP — odoo.com/documentation/17.0/applications/inventory_and_mrp/inventory.html — routes, push/pull rules, removal strategies, inter-warehouse transit as a virtual location.
  • SAP S/4HANA MM-IM Best Practice — SAP Learning Hub — goods receipt against PO, in-transit stock, period lock at material ledger level, four-eyes for SO approval.
  • Oracle NetSuite SCM — multi-location inventory, item receipts vs bills, demand planning. NetSuite's "Transfer Order" mirrors the current Mutasi Stok flow.
  • Toast Kitchen Display & Inventory — toasttab.com — modifier exclusions as signed BOM deltas, blind inventory counts, period close reports.
  • Square for Restaurants — squareup.com/us/en/restaurants — multi-location inventory, modifier-level stock deduction, real-time depletion.
  • Multi-echelon inventory theory — Clark & Scarf (1960), "Optimal Policies for a Multi-Echelon Inventory Problem", Management Science; Zipkin (2000), Foundations of Inventory Management. The base for the "ROP/ROQ + safety stock + MOQ" thinking in the FRD's §5.3.
