Critical Runtime Error Variable used before declaration in yield.ts
src/lib/server/yield.ts — createYieldConversion()
The variable targetNames is used in the ledger IN note string on the line creating the stock ledger entry for the target ingredient, but targetNames is only declared as an empty const object at the very bottom of the file (line ~160), after it's already been referenced. This will cause a runtime error or the name will always be undefined.
// Used here (around line 130): notes: `Yield: produksi → ${targetNames[data.targetIngredientId] ?? data.targetIngredientId}...` // Declared here (at bottom of file, line ~160): const targetNames: Record<string, string> = {};
Fix: Move the targetNames declaration and population (the loop that fetches target ingredient names) to before the ledger IN insertion, similar to how getYieldConversions does it.
Critical Type Safety Stock opnames passed as `any` in dashboard
src/routes/_layout/dashboard.tsx — line 163
The stockOpnames data from the API is cast as any when passed to computeDiscrepancies(). The actual data shape from getDashboardData includes nested items with variancePercentage as a string (from DB), but the computeDiscrepancies function expects variancePercentage as number | undefined. This could cause incorrect filtering (e.g., Math.abs("5") > 3 works by coercion, but Math.abs("0") > 3 would fail silently).
const discrepancies = computeDiscrepancies(stockOpnames as any, ingredients, branches);
Fix: Define a proper type for the dashboard data return value and remove the as any cast. Ensure variancePercentage is properly converted to number in the compute function.
Critical Data Integrity Duplicate markNotificationRead function
src/lib/server/approvals.ts & src/lib/server/system.ts
Two server functions named markNotificationRead exist in different files (approvals.ts and system.ts). They have different implementations — the one in system.ts includes a logSystemAction call and doesn't filter by userId, while the one in approvals.ts filters by userId. The import in NotificationBell.tsx comes from system/server, but the one in approvals.ts is unused. This is a naming conflict that could cause confusion.
// approvals.ts: export const markNotificationRead = createServerFn({ method: "POST" }) .handler(async ({ data }) => { const user = await requireAuth(); await db.update(systemNotifications).set({ isRead: true }) .where(and(eq(systemNotifications.id, data.notificationId), eq(systemNotifications.userId, user.id))); return { success: true }; }); // system.ts: export const markNotificationRead = createServerFn({ method: "POST" }) .handler(async ({ data }) => { const user = await requireAuth(); await db.update(systemNotifications).set({ isRead: true }) .where(eq(systemNotifications.id, data.id)); // No userId filter! await logSystemAction(user, "Mark Notification Read", ...); return { success: true }; });
Fix: Remove the duplicate from approvals.ts. The system.ts version should also add a userId filter to prevent users from marking other users' notifications as read.

The markNotificationRead function in system.ts updates the notification without checking that it belongs to the authenticated user. Any authenticated user could mark any other user's notification as read by providing a valid notification ID.
