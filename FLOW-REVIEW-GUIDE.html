This document is a map of every primary business flow in the repository, with the exact files to open and the invariants to check as you read. Each flow lists the steps in execution order, the role gates, and a trap you should specifically verify. The codebase is a restaurant POS + SCM (supply chain) system for an Indonesian F&B group, so amounts are integer Rupiah and several flows are explicit finite-state machines.

How to use this during review

  1. Pick a flow below; open the file:line anchors in your editor.
  2. Trace each step in the order listed — most flows span a server file + a route file.
  3. Check the trap / invariant call-outs; they are the historically fragile spots.
  4. Run the self-checks where they exist: npx tsx src/lib/server/scm-transfer-fsm.selfcheck.ts.

Authentication & login flow

Login is a custom PIN layer bolted onto Better-Auth. There are four distinct entrypoints, not one. This is the most security-sensitive code in the repo — review it carefully.

File anchors src/lib/auth.ts — Better-Auth setup
src/lib/auth-plugins/pin-auth.ts — PIN endpoints
src/routes/login.tsx — the login UI
src/lib/auth-client.ts — client calls
Self-check The trustedOrigins hack in auth.ts:67 exists because of a signout 403 bug. Note it does weaken CSRF origin checks.
  1. Branch login (two-step). /branch-pin-verify (pin-auth.ts:102) validates the branch code + 4-digit PIN, then returns the branch's staff names. UI shows a name picker.
  2. Staff selection. /branch-login (pin-auth.ts:241) finds-or-creates a branch_admin user from the chosen name (email <branch>_<name>@staff.omoiyari.net) and sets the session cookie.
  3. Non-branch PIN login. /non-branch-pin-login (pin-auth.ts:168) for super_admin / admin_pusat / central_kitchen / area_manager — a single globally-unique PIN identifies the user directly (no name picker).
  4. Email/password (Better-Auth native). /api/auth/$.ts — standard sign-in, passkey supported.
  5. Session resume. The browser session cookie is read on every server function via requireAuth() / requireRole().
Trap — plaintext PINs Branch PINs are compared in plaintext (pin-auth.ts:132, marked TODO(security)). User PINs (for non-branch roles) are stored on the users table likewise. Verify no logging leaks the PIN and decide whether hashing is in scope for this review.
Trap — role gate divergence signInWithPin (pin-auth.ts:21) exists but its role filter is commented out (pin-auth.ts:39), so it accepts any active user by PIN. Confirm it is actually unused, or it is an auth bypass.

Role model & navigation

Roles (userRoleEnum): super_admin, admin_pusat (central HQ), area_manager, branch_admin, central_kitchen. Authorization is enforced in two layers and they are not the same thing — keep that distinction in mind for every flow below.

Two boundaries
  • Role boundary — checked inside the FSMs (rule.actors).
  • Branch boundary — checked upstream by server fns (assertTransferAccess, requireBranch...).
A flow is only safe when both are reviewed. The transfer FSM comment at scm-transfer-fsm.ts:218 says so explicitly.
  • super_admin is silently added to every allowed-actor list at dispatch time — FSM emergency override. Verify this is intended everywhere (e.g. it bypasses area_manager review on Mutasi).
  • admin_pusat is never an actor on Mutasi transfers (branch↔branch) — but is on SCM procurement. Easy to confuse the two.
  • Branch visibility of recipes uses a "no assignment = visible everywhere" rule (pos.ts:50-55). Confirm this matches product intent.

POS order creation

The money path. src/lib/server/pos.ts → createOrder. All mutations run inside one db.transaction with FOR UPDATE row locks on inventory to prevent double-spend.

  1. Validate & resolve ingredients. resolveNewItemIngredients walks each item's recipe BOM + selected modifiers + exclusions to a flat ingredient list.
  2. Compute COGS & totals. Per-item COGS is stored as cogsAtTransaction = round(totalCogs/qty) (pos.ts:419). Watch integer rounding.
  3. Insert order + order_items + modifiers + exclusions in the same tx (pos.ts:405-442).
  4. Deduct inventory with locks. Per-ingredient net delta is summed across items; FOR UPDATE lock taken per ingredient (pos.ts:444-493); a stockLedger row is written.
  5. Negative-stock alert. If an ingredient would go negative, a per-area-manager alert notification is queued outside the tx (pos.ts:498-515).
Trap — exclusion restore direction The stock ledger records exclusions as IN/restore (pos.ts:482-489). Confirm the sign convention: an "exclude onion" should not deduct onion, and on void should restore correctly. This is the single easiest place to get inventory math wrong.
Trap — negative stock is allowed The order is not blocked when inventory would go negative; it only raises an alert. Decide whether that is correct business behaviour or a gap.

Cancel-request lifecycle (void)

Order cancellation is deliberately split into four states so a cashier cannot unilaterally void: Pending → Approved → Executed, plus Rejected. See src/lib/server/pos.ts:993-1195.

  1. createCancelRequest — cashier opens a request (Pending).
  2. approveCancelRequest — a manager approves; order is not yet voided, cashier is notified to press "Batal".
  3. rejectCancelRequest — manager rejects.
  4. executeApprovedCancel — cashier runs it; in one tx the request→Executed, the order→Void, and restoreInventoryForVoid puts stock back.
Trap — double execute executeApprovedCancel guards on status==="Approved" and order.status!=="Void" (pos.ts:1154-1159) but the two checks are separate reads/updates, not a single locked tx around the status read. Confirm there is no TOCTOU where two cashiers execute the same approved request concurrently. The order status write is in the tx; the request status read is before it.

SCM Procurement FSM (ADR 0002)

The new central-kitchen procurement flow. The spec lives in a transition table at src/lib/server/scm-fsm.ts:91; transition() (scm-fsm.ts:244) is the only mutator and runs all effects + audit inside one row-locked tx.

Draft submit→Pending · cancel→Cancelled BA, SA
Pending open-review→UnderReview · withdraw→Draft · cancel AP/SA review
UnderReview reject→Rejected · accept-and-ship→InTransit (writes stock) · cancel AP/SA
InTransit mark-delivered→Delivered · cancel (reverse in-transit) BA/SA
Delivered open-receive→ReviewingSJ · cancel (reverse) BA/SA
ReviewingSJ finish-receive→WaitingForPayment (sets received qty, writes stock, waste, invoice snapshot) · cancel BA/SA
WaitingForPayment mark-paid→Finished · cancel AP/SA
Rejected / Finished / Cancelled terminal — no outgoing transitions
Invariant — item edits are state-gated updateItem (scm-fsm.ts:385) enforces: CA fields only in UnderReview; BA received/rejected fields only in Delivered/ReviewingSJ; quantity only in Draft. Verify the UI cannot reach these fields outside the allowed state (the guard is server-side but the UX must also hide them).
Trap — cancel effect direction Different cancel points run different reversal effects (reverseInTransitOnCancel vs reversePendingReviewOnCancel). Confirm each reversal exactly undoes the forward effect for that entry point; a missed reversal silently corrupts inventory/ledger.

Mutasi — branch↔branch transfer FSM (ADR 0006)

Mirrors the procurement FSM but for stock movement between two outlets, and the role matrix is different. Spec at src/lib/server/scm-transfer-fsm.ts:114. A pure-logic self-check exists: src/lib/server/scm-transfer-fsm.selfcheck.ts — run it.

Invariant — super_admin & admin_pusat transitionTransfer (scm-transfer-fsm.ts:248) allows super_admin on every transition but never admin_pusat. The self-check asserts exactly this. If you change the role matrix, update the SPEC in the self-check too.
Trap — branch boundary is NOT in the FSM The FSM only checks role. The specific branch_admin must be from the Sender or Receiver branch, enforced by assertTransferAccess upstream (scm-transfers.ts:361). If a server fn forgets to call it, a BA at branch A could move branch B's stock. Verify every transfer entrypoint calls the guard.

Legacy SCM — PR → PO → DN → Invoice

The older supply-chain path in src/lib/server/scm.ts (distinct from the FSM above). Status checks are inline throw new Error(...) guards rather than a table. Review each transition's precondition:

  • processPR — PR must be Pending or Approved (scm.ts:326).
  • receivePO — PO must be Sent or Partial (scm.ts:619).
  • shipDN — delivery note must be Picking (scm.ts:891).
  • receiveDN — must be In Transit or Partial Received (scm.ts:995).
  • Transfers (legacy stock_transfers) gates at scm.ts:1746/1796/1854/1947.
Trap — two SCM systems coexist There is a new FSM-based procurement (§5) and a legacy procurement in scm.ts. Confirm which routes point at which, and that they don't both write the same tables / stock. Double-counting here is a classic financial bug.

Inventory, stock opname & audit

  1. Stock opname submit. Records counted quantities; on discrepancy flagged Under Investigation (inventory.ts:419).
  2. Audit inventory (theoretical). getAuditInventory (audit-inventory.ts:26) recomputes expected consumption from completed orders → BOM. Compare against actuals.
  3. Approve / resolve. approveStockOpname (inventory.ts:453) only proceeds from Under Investigation (inventory.ts:593) and writes the adjustment.
Trap — "Completed" only The audit theoretical calc filters orders.status = "Completed" (audit-inventory.ts:34) and ignores voided/cancelled — but the order-create flow deducts inventory at creation, not completion. If an order is voided, inventory was restored but it still won't be in "Completed", so the theoretical-vs-actual gap must be read with that in mind.

Finance & period control

getFinanceSummary (finance.ts:44) is gated to super_admin only. It sums orders + manual revenues/expenses + waste + transfers. Period control (/period-control) closes accounting periods.

Trap — role scope of finance Finance summary requires super_admin. Confirm admin_pusat / area managers have no path to the same numbers through a different fn (e.g. a branch-scoped fn that aggregates globally). Cross-check finance.ts callers.
Invariant — integer currency All money is integer (Rupiah, no sen). numeric is deliberately avoided per project convention. Verify no new column uses numeric (it maps to string in Drizzle and breaks math).

Document codes & master data

generateDocumentCode (document-codes.ts:36) produces <PREFIX>/<BRANCH>/<ddmmyy>/<serial> using an atomic ON CONFLICT DO UPDATE serial counter that resets daily.

Trap — preview vs generate previewNextDocumentCode (document-codes.ts:72) does not increment. If the UI shows a preview and then the real generate runs, a concurrent create could collide on the same serial — verify callers don't treat the preview as reserved.
  • Seeding: vp run migrate-csv is the source of truth; seed-data.ts is deprecated/stale. On a live DB, several migrations TRUNCATE … CASCADE and wipe operational data — never run full migrate-csv against production without a pg_dump first.
  • Recipe branch visibility: recipeBranches governs which outlet sees which menu item (no assignment = everywhere).

Cross-cutting things to notice

1 · Transactions & locks

Every money/stock mutation should be in a db.transaction with FOR UPDATE on the rows it reads-then-writes. Spot-check that new code paths don't sneak an UPDATE outside the tx (notifications are intentionally outside, which is fine).

2 · Audit logging

FSM transitions and cancels write audit rows. Verify the audit column captures fromState/toState/actor — it's the only forensic trail for stock disputes.

3 · Notifications are best-effort

Alerts/notifications are written outside the main tx, so a tx rollback won't leave a dangling notification but a notification failure won't roll back the business action either. Confirm that's acceptable per flow.

4 · Server functions = the API

There are no separate REST controllers; each createServerFn in src/lib/server/*.ts is an endpoint. Review authorization at the top of every handler (requireAuth / requireRole / branch assert). A missing guard = unauthenticated mutation.

5 · Two FSMs, two self-checks

Procurement FSM has no self-check file (only the transfer one does). Consider writing a parallel scm-fsm.selfcheck.ts so the procurement state matrix is locked the same way.
