SCM as a Finite State Machine

Your win in this lesson: you can draw the full PR→SJ→Invoice lifecycle as a state diagram, name which actor triggers each transition, and explain why a formal FSM is the tool that keeps this process from turning into spaghetti.

1. What Is a Finite State Machine?

A finite state machine (FSM) is a model of computation where a system can be in exactly one of a finite set of states at any time. It can only move from one state to another through a defined transition, and each transition is triggered by an event (an action by a user or the system).

Three elements
  • States — the "modes" the system can be in (e.g., Pending, In Transit)
  • Transitions — arrows from one state to another, labelled with the event
  • Events — what causes a transition (a button click, a timer, a webhook)
Why FSMs belong in your SCM
  • Prevents illegal transitions (e.g., invoicing before receiving)
  • Each state tells the UI exactly which buttons to show and which actor can press them
  • Audit trail: every state change becomes an event log entry
  • Your code becomes a switch(state) instead of a forest of if/else
Real talk: the current Omoiyari codebase has state machines (PR status enum, SJ status enum, invoice status enum), but they are not enforced uniformly. The PR can go from Draft directly to Processed without an Approved intermediate — because the code doesn't model the review step as a separate state. What you're proposing in your redesigned process adds that missing state — and that's exactly the right call.

4. Why This Matters in the Code

Without a formal FSM, your SCM server functions look like this:

// 🚫 Without FSM discipline
async function handleAction(prId, action, user) {
  const pr = await getPR(prId);
  if (action === 'review') {
    if (pr.status !== 'Pending') throw Error('wrong state');
    // ... lots of logic
    if (someCondition) pr.status = 'UnderReview';
    else pr.status = 'Rejected';
  }
  if (action === 'accept') {
    if (pr.status !== 'UnderReview') throw Error('wrong state');
    // ... even more logic, also creates SJ
  }
  // ... every action has its own state guard
}

With a formal FSM, it becomes:

// ✅ With FSM — states, actors, and transitions are explicit
const transitions = {
  Pending: {
    'open-review':      { to: 'UnderReview',  actor: ['admin_pusat', 'super_admin'] },
  },
  UnderReview: {
    'reject':           { to: 'Rejected',      actor: ['admin_pusat', 'super_admin'] },
    'accept-and-ship':  { to: 'InTransit',     actor: ['admin_pusat', 'super_admin'],
                          effects: ['createSJ', 'createInTransit'] },
  },
  // ...
};

async function transition(prId, event, user) {
  const pr = await getPR(prId);
  const rule = transitions[pr.status]?.[event];
  if (!rule)                     throw new Error(`Cannot ${event} from ${pr.status}`);
  if (!rule.actor.includes(user.role)) throw new Error('Not authorized');
  for (const effect of (rule.effects ?? [])) {
    await applyEffect(effect, pr, user);
  }
  await updatePR(prId, { status: rule.to, lastEvent: event, updatedBy: user.id });
  await logAudit({ action: event, from: pr.status, to: rule.to, userId: user.id });
}
This is the pattern you want. A lookup table of { currentState: { event: { to, actor, effects } } } is the most readable, testable, and auditable way to enforce your process. Every possible transition is visible at a glance. No hidden branches. No forgotten state guards.

Benefits for your specific flow

  1. No more "can I do this?" bugs. The FSM table defines exactly what each actor can do at each state. The code will never let a BA see a "Mark Delivered" button.
  2. Each state has a single owner. "Under Review" means "CA is working". BA can watch but can't interfere. The FSM enforces this turn-taking.
  3. Real-time view becomes trivial. BA seeing "Under Review" is just reading the PR's { status, lastEvent, updatedBy } fields and rendering a different component.
  4. Audit trail is automatic. Every transition is logged: who did what, from what state to what, at what time.
  5. Adding new states is safe. Want to add a "Partially Received" state? Add it to the FSM table, wire the transition, and the rest of the code doesn't change.

7. Summary — What to Take Forward

The FSM table is your single source of truth. Build it early. It replaces a hundred if (status === X && role === Y) checks with one function.
  1. Every state has one owner. Under Review = CA's turn. Reviewing SJ = BA's turn. Never ambiguous.
  2. Every transition has a guard. Actor + current state. No exceptions.
  3. UI is derived from the FSM. actor × state → component. Not the other way around.
  4. The interactive table is a reusable primitive. Different modes for different states, same component.
  5. Real-time visibility is free. BA seeing CA's review = client polls the PR status and renders the read-only version of the same table.
  6. Invoice shows both sides. Accepted items (chargeable) + rejected items (Rp 0 with reason) in one document. No separate credit notes.
