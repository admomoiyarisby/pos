Trace One SKU Through SCM

Your win in this lesson: given one bag of rice requested by a branch, you can say which document owns it, where the stock sits, and when it becomes invoiceable — and you can spot the gap between the FRD's intended flow and the current implementation.

1. The Two Flows, Side by Side

The FRD names a four-document chain (PR → PO → SJ → Invoice) as the canonical restocking cycle. The implementation treats PO as optional for the internal restocking path and lets a PR create an SJ directly. Read the two diagrams and the gap is the difference between the green "intended" path and the purple "actual" path.

Gap to remember: the FRD says the PO step is canonical; the code lets you skip it. This is a defensible design (ERPNext treats PO as optional for internal stock transfers too) but the policy is not written down anywhere — the next lesson will work through how to make it explicit.

2. State Machines You Can Read Off the Code

State diagrams are how you answer "what can happen to this document next, given its current status?" The two most consequential state machines for the SCM flow are the PR and the SJ.

The Partial Received state was added in Phase 2 of the supply-chain fix plan to support multi-receive calls on the same SJ.

3. The Five Quantities That Travel With an Item

Every delivery-note item carries five quantity columns. They look like duplication, but each one has a single specific job. Reading them off the schema: 

quantity           requested / order baseline
readyQuantity      how much Central says is available
pickedQuantity     how much is actually loaded and shipped
receivedQuantity   how much the branch accepts into usable stock
rejectedQuantity   how much the branch rejects (broken / wrong / not SOP)

The invoice line quantity is always receivedQuantity. That is the FRD's "actual base" rule (§4.2.4) and it is correctly implemented in generateSCMInvoice (src/lib/server/scm.ts:1437).

4. What Happens at Each Transition, in Plain English

  1. Smart reorder suggests. 30-day OUT total ÷ 30 × ROQ days, rounded up to MOQ. Defaults ROP 3 / ROQ 5. Source: reorder.ts.
  2. Branch creates PR. Status starts Pending. Branch admins are forced to their own branch; every item must respect MOQ. Source: scm.ts createPurchaseRequisition.
  3. Center processes PR. Once Processed, branch edit is blocked (branch admin may only edit Draft or Pending). With alsoCreateSJ: true the code also writes an SJ in Picking — note: no in-transit record is created here, only the document.
  4. SJ ships stock into transit. At the Picking → InTransit transition, the source inventory is reduced, an OUT ledger entry is written, and an in_transit_inventory row is created. This is the moment the item is physically no longer counted at Central but not yet counted at the branch.
  5. Branch receives reality, not theory. The receiving form records accepted and rejected quantities. Accepted quantity increases destination inventory. Rejected quantity takes one of three dispositions: Return to Source (returns stock + writes mirror ledgers), Scrap (auto-creates a waste entry), or Quarantine (ledger note only — no real bucket yet).
  6. Invoice follows accepted quantity. generateSCMInvoice reads receivedQuantity per item and refuses to issue an invoice with zero total amount. Source: src/lib/server/scm.ts:1437–1545.
  7. Admin Pusat reviews, then pays. The DN has a reviewedByAdminPusat flag that gates the invoice button. paySCMInvoice flips the status and stamps paidAt.

5. Interactive Check

A branch requested 25 kg rice. Central picked and shipped 20 kg. The branch received 18 kg and rejected 2 kg as Scrap. What quantity should the SCM invoice charge?

6. Open Gaps to Carry Forward

  • Quarantine is named, not modeled. A real quarantine_inventory table is needed before a "quarantined" item can be a stock bucket with its own release action. Until then, Quarantine is a recorded exception, not a location.
  • PO is optional in implementation. The FRD's canonical chain is PR → PO → SJ → Invoice. The code lets you skip PO. The right next decision is to make that policy explicit in writing — either keep PR → SJ direct and update the FRD, or hard-gate the PO step in code.
  • Edit Invoice is missing. FRD §4.2.4 says Super Admin and Admin Pusat may edit an invoice for discrepancy cases. The current code has no updateSCMInvoice. The safe pattern is a "cancel + reissue" with a chained audit reference.
