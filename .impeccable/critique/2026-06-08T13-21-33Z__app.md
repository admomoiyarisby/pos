## Overall Impression

Omoiyari POS is a serious, well-architected operational tool. The restrained color system, consistent typography, and role-gated UI are aligned with the product's "Efficient, Trustworthy, Calm" brand. The biggest opportunity is tightening component consistency — the app uses two modal systems side by side, buttons are built three different ways, and some smaller components have hardcoded colors that break in dark mode. These aren't critical blockers, but they prevent the UI from feeling as polished as the backend architecture clearly is.

## What's Working

1. **Restrained palette with correct contrast.** The cool-gray neutral system is well-considered in both light and dark modes. The design system correctly reserves saturated colors for data visualization only. Body text contrast is adequate in both themes.

2. **Role-gated navigation and actions.** The sidebar correctly hides irrelevant groups per role, action buttons gate on `canX` booleans, and `RoleGuard` wraps entire pages. This isn't just UI hiding — unauthorized actions are structurally impossible.

3. **POS keyboard shortcuts.** The POS register has thoughtful shortcuts: `Escape` clears cart, `Enter` checkouts, `/` focuses search, `1–9` selects menu items. This is the kind of power-user consideration that separates tools from toys.

## Priority Issues

### [P1] Two Modal Systems with Inconsistent Behavior

- **What**: The app has two distinct modal implementations. The custom `Modal.tsx` (used in POS shift, void, payment confirm, and most admin CRUD modals) uses manual overlay handling, a `<h2>` title, and a close button in the header. The Radix-based `Dialog` (in `dialog.tsx`, used in users delete-info, command palette) uses proper ARIA attributes, portal rendering, `DialogTitle`/`DialogDescription`, and a different close button pattern. They have different border radii, different padding, different backdrop, and different keyboard handling (the Radix version traps focus properly; the custom one doesn't).
- **Why it matters**: Users perceive component inconsistency as lack of polish, even subconsciously. Keyboard users will notice that some modals trap focus and others don't. The aesthetic difference (8px vs 12px corners, `shadow-lg` vs `shadow`) breaks the visual system.
- **Fix**: Choose one modal system and migrate all instances. The Radix `Dialog` component is more accessible and already has correct ARIA — it should be the canonical one. The custom `Modal` should be replaced by `Dialog` everywhere.
- **Suggested command**: `/impeccable harden app`

### [P1] Hardcoded Light-Mode Colors in Dark Mode Contexts

- **What**: Several components use hardcoded Tailwind colors that will not adapt: `Badge` variants `success`/`warning` use `bg-green-500`/`bg-amber-500`; `$soId.tsx` uses `bg-amber-50`, `bg-amber-50 text-amber-800`, `bg-blue-50 text-blue-800`; `stock-transfers` uses `bg-emerald-600 text-white`, `bg-red-600 text-white`, `bg-blue-600 text-white`, `bg-slate-500 text-white`; `stock-opname` uses `text-green-600`/`text-red-600`; `pos.tsx` uses `bg-amber-600 text-white`, `bg-purple-600 text-white`. All of these will render as light-mode colors in dark mode with unknown contrast.
- **Why it matters**: Dark mode is a core design requirement for kitchen environments. Hardcoded light colors that fail in dark mode break the product's core accessibility promise. The variance row `bg-amber-50` will be invisible in dark mode.
- **Fix**: Replace hardcoded colors with theme-aware CSS variable equivalents. Define proper semantic color tokens for approve/reject/variance/info.
- **Suggested command**: `/impeccable colorize app`

### [P1] Component Vocabulary Inconsistency (Buttons, Forms, Cards)

- **What**: The `Button` component has 6 variants and 8 sizes, yet many pages use raw `<button>` elements with inline classes. `SuccessModal.tsx` and `ModifierModal.tsx` use raw `<button>` elements. `stock-transfers` uses inline `bg-emerald-600 text-white` buttons. `Pagination` uses raw buttons. Some modals use `Button` while others use raw buttons.
- **Why it matters**: The product register explicitly bans this: "Inconsistent component vocabulary across screens. If the 'save' button looks different in two places, one is wrong." It also makes future theming changes require edits in dozens of places instead of one.
- **Fix**: Migrate all raw `<button>` elements to the `Button` component. Migrate inline card markup to the `Card` component. Use `Input`, `Select`, `Label` components everywhere.
- **Suggested command**: `/impeccable polish app`

### [P2] Data Table Action Columns Violate Working Memory Limits

- **What**: In `stock-transfers/index.tsx`, each row can display up to 6 action buttons (Approve, Tolak, Kirim, Terima, Batal, detail arrow). This exceeds the 4-item working memory limit. The buttons use different colors (emerald, red, blue, slate) which adds visual noise.
- **Fix**: Group related actions under a single "Actions" dropdown menu visible on hover/focus, or consolidate by status.
- **Suggested command**: `/impeccable layout app`

### [P2] POS Cart Icon-Only Buttons Lack Labels

- **What**: Cart item increment/decrement buttons use `<Plus>` and `<Minus>` icons without `aria-label` attributes. Screen readers get no context.
- **Fix**: Add `aria-label="Tambah jumlah"` and `aria-label="Kurangi jumlah"` to the increment/decrement buttons.
- **Suggested command**: `/impeccable clarify app`

### [P2] Fragile POS Layout (Negative Margins)

- **What**: The POS page uses `-m-4 md:-m-6` to counteract AppShell padding. The header height is hardcoded as `calc(100vh - 3rem)`. This breaks if parent layout changes.
- **Fix**: Make AppShell accept a `fullscreen` prop that removes padding for pages like POS.
- **Suggested command**: `/impeccable layout app`

### [P3] Modal Overlay Click Behavior Mismatch

- **What**: Custom `Modal.tsx` closes on overlay click, Radix `Dialog` does not auto-close on overlay click. Inconsistent dismissal behavior.
- **Fix**: Make the Radix Dialog overlay dismiss on click (via `onPointerDownOutside`).
- **Suggested command**: `/impeccable harden app`

## Persona Red Flags

### Alex (Power User)

- **Good**: POS keyboard shortcuts exist
- **Red flags**: No global keyboard shortcuts outside POS. No bulk edit/select in data tables. No command palette (the `Command` component exists but isn't wired to a global shortcut). Table action columns with 5+ buttons force a clicking workflow. No `Ctrl+S` to save forms.

### Jordan (First-Timer)

- **Good**: Indonesian labels throughout, clear sidebar groups
- **Red flags**: No onboarding or guided tour for any role. Jordan faces a full POS grid with no explanation of what to do first. The "Buka Shift" prerequisite is not explained. Two modal systems with different behaviors will confuse Jordan.

### Sam (Accessibility-Dependent)

- **Good**: Dark mode support, Radix Dialog has proper ARIA
- **Red flags**: Custom `Modal` doesn't trap focus (keyboard users can tab behind overlay). Icon-only increment/decrement buttons lack `aria-label`. Variance direction uses color alone (`text-green-600`/`text-red-600`) with no icon or text prefix.

## Minor Observations

1. Auto-close on SuccessModal: 4-second timer has no pause-on-hover — user can't review details.
2. Print template HTML in supplier-deliveries uses hardcoded light colors but it's a separate print context.
3. The `bg-amber-50` variance row highlight in `$soId.tsx` is invisible in dark mode.
4. Sidebar collapse icons swap with no animation — a quick rotation would feel more intentional.
5. DataTable dedup logic hints at real duplicate-key issues in the data layer.

## Questions to Consider

1. **Two modals or one?** Is there a reason both `Modal.tsx` and `Dialog` exist, or is this accumulation from two different development phases? Converging on one would immediately improve consistency.

2. **Are green/amber badges worth the design system violation?** The `success`/`warning` badge variants are convenient, but they introduce saturated colors the design system explicitly excludes. Could status be communicated through the existing neutral palette with icons?

3. **What would a "dark mode pass" look like?** The dark theme CSS variables are well-structured, but the hardcoded inline colors suggest it's never been systematically tested. A full page-by-page dark mode audit would likely reveal more.
