Skenario 04 — Mutasi Stok Antar Cabang

Surat jalan cabang→cabang (FSM, ADR 0006)
Bahasa Indonesia · gaya Tufte · sumber: scm-transfer-fsm.ts

← Kembali ke indeks

Berbeda dari Skenario 03 (beli dari supplier ke pusat), ini pergerakan stok antar dua outlet. FSM-nya mirip tapi matriks role berbeda dan — yang paling penting — ada dua batas keamanan: batas role (di FSM) dan batas cabang (di server fn, di luar FSM). Skenario ini punya self-check nyata yang harus Anda jalankan.

Invarian — super_admin ya, admin_pusat TIDAK transitionTransfer (scm-transfer-fsm.ts:248) mengizinkan super_admin di semua transisi, tapi admin_pusat tidak pernah jadi actor di Mutasi (Q4/Q8). Self-check menegaskan ini. Jangan samakan dengan Skenario 03 di mana admin_pusat ikut review.

A. Buat surat jalan (Draft)

Dua cabang createStockTransfer (scm.ts:1676) menuntut fromBranchId ≠ toBranchId (scm-transfers.ts:205). Self-check keamanan cabang ada di assertTransferAccess (scm-transfers.ts:361): "sender" → BA di fromBranch, "receiver" → BA di toBranch, "either" → salah satu. Lazy DB FSM Mutasi men-lazy import db (scm-transfer-fsm.ts:29) agar tabel transisi bisa di-self-check tanpa DB.
  1. BA cabang pengirim buat transfer: pilih cabang tujuan + items bahan → createStockTransfer.
  2. Server validasi cabang beda; insert scmTransfers status SuratJalanDraft + items.
  3. BA pengirim edit quantity item di Draft via updateTransferDraftItems (terpisah dari transition).

B. Submit → review area manager

  1. BA klik submit → submit → SuratJalanDraft→PendingAMReview. Actor BA.
  2. Area Manager (yang memegang salah satu cabang) klik approve → approve → PendingAMReview→Approved, catat reviewingById + approvedAt (scm-transfer-fsm.ts:261). Atau reject → Rejected, atau withdraw → Draft.
Jebakan — batas cabang TIDAK di FSM FSM hanya cek role (AM). Apakah AM ini benar memegang cabang pengirim atau tujuan dicek di luar FSM oleh assertTransferAccess (scm-transfer-fsm.ts:218). Bila server fn lupa memanggil guard ini, AM sembarang bisa setujui transfer antar cabang orang lain. Verifikasi setiap entrypoint memanggil guard.

C. Kirim (Approved → InTransit)

  1. BA pengirim klik ship → ship → Approved→InTransit. Efek writeTransferInTransitInventory (stok keluar dari gudang pengirim).
  2. AM dapat cancel → reverseTransferInTransitOnCancel.

D. Terima & review SJ (Delivered → WaitingForPayment)

  1. BA pengirim klik "mark delivered" → mark-delivered → InTransit→Delivered (efek moveTransferToPendingReview).
  2. BA pengirim klik "open receive" → open-receive → Delivered→ReviewingSJ.
  3. Isi received/rejected per item → updateTransferItem (hanya di Delivered/ReviewingSJ, scm-transfer-fsm.ts:376).
  4. BA klik "finish receive" → finish-receive → ReviewingSJ→WaitingForPayment. Efek: setReceived + writeReceivedStock + writeRejectedWaste + generateTransferInvoiceSnapshot (scm-transfer-fsm.ts:162-171).

E. Bayar (WaitingForPayment → Finished)

  1. BA klik "mark paid" → mark-paid → WaitingForPayment→Finished. Efek markTransferInvoicePaid, catat paidById.
  2. Terminal Finished.

F. Self-check (wajib jalankan)

npx tsx src/lib/server/scm-transfer-fsm.selfcheck.ts
  1. Self-check memvalidasi: tiap (state,event) di SPEC ada di tabel dengan to/actors benar; tidak ada transisi liar; state terminal tanpa keluar; availableTransferEvents per (state,role) benar.
  2. Khususnya menegaskan: super_admin lihat semua event; admin_pusat tidak lihat satupun (scm-transfer-fsm.selfcheck.ts:147-173).
  3. Jika FAIL, jangan lanjut review sampai matriks role diperbaiki — self-check adalah spesifikasi tertulis dari FSM ini.
Invarian — jaga SPEC & tabel sinkron Bila Anda mengubah matriks role di transferTransitions, Anda juga harus ubah SPEC di self-check. Kalau tidak, self-check akan FAIL atau — lebih buruk — lulus padahal spesifikasi sudah usang.

G. Mekanisme transitionTransfer()

  1. transitionTransfer() (scm-transfer-fsm.ts:227) buka tx, SELECT … FOR UPDATE (:236-240).
  2. Cari rule; bila tak ada → InvalidTransferTransitionError; actor tak diizinkan (dan bukan super_admin) → TransferUnauthorizedError (:244-252).
  3. Jalankan efek, update status + audit + (notifikasi dalam tx) (:292-320).
Checklist akhir scenario 04
  • Jalankan self-check → PASS.
  • Setiap entrypoint Mutasi memanggil assertTransferAccess (batas cabang).
  • admin_pusat tak pernah jadi actor; super_admin bisa semua.
  • Cancel reversal per titik arahnya benar.
  • Edit item transfer state-gated (Draft vs Delivered/ReviewingSJ).
