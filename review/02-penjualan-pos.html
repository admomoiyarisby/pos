Skenario 02 — Penjualan POS & Pembatalan

Jual resep (potong stok terkunci) → cancel request → void + restore

Lanjutan Skenario 01: resep yang sudah dibuat dijual di kasir. Alur ini adalah jalur uang dan jalur stok. Semua mutasi berjalan dalam satu transaksi terkunci (FOR UPDATE) agar tidak ada double-spend. Fokus review: keamanan stok, arah restore eksklusi, dan alur pembatalan 3-langkah.

A. Persiapan kasir & menu

Otorisasi POS memakai requireAuth() (bukan role spesifik) — siapa pun yang punya sesi bisa order. Branch dibatasi dari sisi UI: kasir cabang hanya melihat menu cabangnya lewat getPosMenu. Visibility getPosMenu (pos.ts:39) menyembunyikan resep yang di-assign ke cabang lain tapi bukan cabang ini; resep tanpa assignment tampil di semua cabang (pos.ts:50-55).
  1. Kasir login PIN cabang → dapat sesi branch_admin dengan branchId.
  2. Buka /pos. Loader memanggil getPosMenu (pos.ts:39) + getBranches, getVouchers, getInventory (pos.ts:58-61).
  3. Pilih channel (Dine-in / Gofood / Grabfood / ShopeeFood / TikTok — pos.ts:48).
  4. Tambah item dari menu → MenuGrid memanggil createOrder saat checkout.
Invarian — menu hanya resep Active getPosMenu memfilter recipes.status = "Active" (pos.ts:48). Resep yang di-soft-delete (Inactive) tak akan muncul di kasir meski recipeBranches mengizinkan.

B. Buat order (createOrder)

  1. createOrder (pos.ts:294) menerima branchId, channel, items[] (tiap item: recipeId, quantity int≥1, price, selectedModifiers[], notes), voucherCode, taxAmount, shiftId (pos.ts:295-309).
  2. Resolve bahan. Untuk tiap item, resolveNewItemIngredients (pos.ts:323) menelusuri resep → BOM + modifier + eksklusi jadi daftar bahan datar beserta cost.
  3. Soft stock check (read-only). Loop per bahan (pos.ts:348-368): bila stok cabang < kebutuhan → push negativeStockAlerts. Tidak memblokir order.
  4. Hitung total. subtotal = Σ price×qty; totalCogs = Σ cost; totalAmount = subtotal − voucherDiscount + tax; MDR dari platformFees (pos.ts:342-379).
  5. Semua tulis dalam 1 tx. (pos.ts:382):
    • Insert orders dengan totalCogs, mdrFee, netSales.
    • Insert orderItems — cogsAtTransaction = round(totalCogs/qty) (pos.ts:419).
    • Insert orderItemModifiers & orderItemExclusions (pos.ts:425-441).
    • Potong stok terkunci: per bahan unik, SELECT … FOR UPDATE (pos.ts:461), hitung net delta lintas item, UPDATE inventory + tulis stockLedger (pos.ts:444-493).
  6. Di luar tx: bila ada alert stok minus → notifikasi ke area manager (pos.ts:498-515).
Jebakan — arah restore eksklusi Stok ledger mencatat eksklusi sebagai IN (restore) saat order (pos.ts:482-489). Artinya: "tanpa bawang" → bawang tidak dipotong. Saat review, konfirmasi resolveNewItemIngredients benar-benar mengurangi bawang dari ingredients net item, supaya ledger tidak menggandakan atau salah memulihkan. Ini titik paling sering salah.
Jebakan — stok minus diizinkan Order tidak diblokir walau stok negatif; hanya alarm. Tentukan apakah ini memang perilaku bisnis yang diinginkan, atau celah. Di lintasan konkuren, dua order hampir bersamaan bisa sama-sama lolos soft-check lalu memotong stok via row-lock — aman secara DB, tapi saldo bisa jadi sangat negatif.

C. Pembatalan — request (kasir)

Kenapa 3 langkah? Agar kasir tidak bisa membatalkan sepihak. Request → Manager approve → kasir eksekusi void. Status: Pending → Approved → Executed, plus Rejected.
  1. Di /pos (history), kasir klik batalkan order → createCancelRequest (pos.ts:993). Menyisipkan baris cancelRequests status Pending.
  2. getActiveRequestsForOrders (pos.ts:1199) melakukan polling status (Pending/Approved) per order untuk badge di UI.

D. Pembatalan — approve (manager)

  1. Manager (role berwenang) buka daftar cancel request → getCancelRequests (pos.ts:1024).
  2. Klik approve → approveCancelRequest (pos.ts:1059):
    • Cek old.status === "Pending" else "sudah diproses" (pos.ts:1071).
    • Set status Approved, approvedBy, approvedAt.
    • Notifikasi ke kasir peminta: "klik tombol Batal untuk menjalankan" (pos.ts:1080).
  3. Order belum void pada tahap ini — hanya request yang berubah jadi Approved.
Invarian — belum void di approve Pemisahan ini krusial: approve hanya mengizinkan, eksekusi yang mengubah stok. Saat review, pastikan tidak ada jalur (tombol/API) yang memanggil void langsung tanpa approve.

E. Pembatalan — execute void (kasir)

  1. Kasir klik "Batal" → executeApprovedCancel (pos.ts:1142):
    • Cek status === "Approved" (pos.ts:1154) — tolak bila belum/disudah eksekusi.
    • Cek order.status !== "Void" (pos.ts:1159).
    • Dalam 1 tx (pos.ts:1161): set request→Executed, set order→Void (dengan voidReason), lalu restoreInventoryForVoid mengembalikan stok + tulis ledger.
  2. Audit STATUS_CHANGE pada orders + cancelRequests (pos.ts:1180-1192).
Jebakan — TOCTOU eksekusi ganda Pengecekan status==="Approved" (pos.ts:1154) dan penulisan status request terjadi di luar lock baris order. Dua kasir menekan "Ba tal" bersamaan pada request Approved yang sama bisa membaca status sama, lalu keduanya menjalankan void → stok ke-restore dua kali. Periksa apakah restoreInventoryForVoid atau tx memegang lock yang mencegah ini (lock ada di tx, tapi baca status di atas tx).

F. Verifikasi & lintasan

  1. Cek orders: status Void, voidReason terisi.
  2. Cek inventory cabang: stok bahan kembali seperti sebelum order (termasuk eksklusi benar arahnya).
  3. Cek stockLedger: ada baris pemulihan (IN) ber-referensi order.
  4. Cek cancelRequests: status Executed, approvedBy & eksekutor tercatat.
Checklist akhir scenario 02
  • Order dalam 1 tx + FOR UPDATE per bahan.
  • Eksklusi restore arahnya benar (tidak potong & tidak ganda).
  • Stok minus hanya alarm (konfirmasi disengaja).
  • Cancel = 3 langkah; void hanya di execute setelah Approved.
  • Tidak ada TOCTOU eksekusi ganda.
